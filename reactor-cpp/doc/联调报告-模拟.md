日期：2026-11-26　环境：macOS 开发机，`reactord --sim`（Unix socket + TCP 127.0.0.1:18080），触屏用无屏预览 `reactor-hmi-shot --server unix:…` 逐页截图。
结论：先修了 4 个已知问题，补了 3 项决定记录里的界面，然后按真实使用顺序造状态、逐页截图，一共找出并修掉 37 处缺陷。

## 1. 怎么跑的

后台：

```
reactord --sim --config /tmp/rxi/cfg --data /tmp/rxi/data --socket /tmp/rxi/hmi.sock \
         --api-config /tmp/rxi/api.json --port 18080 --usb-root /tmp/rxi/media --seconds 7200
```

- `api.json` 开了 TCP，配一个 operator 令牌 `lab-pc`，用来模拟 PC 申请控制权。
- U 盘：`/tmp/rxi/media/HTUSB/` 里放一个空文件 `.reactor-fake-usb`。开发机挂不了真盘，这是新加的开发用约定，见 §3 D32。

场景按时间顺序排，用 Python `http.client` 走 AF_UNIX，写命令都带 Idempotency-Key：

| 阶段 | 做了什么 | 截的页 |
|---|---|---|
| A 开机 | 检查开机报警表和常压读数；PATCH 设置（泄漏测试平衡 1 min / 测量 5 min）；启用 1–6 号；1–3 号关防超调；5 号手动加热 120 ℃；6 号曲线升温 4 段；4 号跑短程序（搅拌 + 升温 35 ℃ + 放空）；程序库存一条并载入 1 号；2、3 号放 6 段 / 12 段曲线升温草稿；用已启用的 1 号发泄漏测试，验证被拒 | leak-setup、chan-quick*、chan-full*、kbd-*、lang-pop、stop-all、prog-1、prog-addstep、prog-curve8/16、prog-param-*、lib-*、set-* |
| B 泄漏测试 | 对停用的 7、8 号做泄漏测试：充压 → 平衡 → 测量 → 判读 → 经排空阀泄压 | leak-run、main-f1/f2（测试中）、leak-pass、leak-result |
| C 气路排队 | 1–3 号同时下发带气路步骤的程序（气密 → 置换 → 搅拌 → 升温 → 充压稳压 → 反应 → 放空）：1 号先拿到气路，2、3 号排第 1、2；PC 经 TCP 申请控制权 → 触屏弹窗 → 本地 grant | main-f1、prog-run、plan-all、plan-one、chan-quick-run、chan-full-run、abort-ask、prog-abort-ask、ctl-request、main-f2（顶栏「PC 控制中」） |
| D 报警 | 导出最近 20 min 到 U 盘；4 号跑一个必然升温超时的程序 → 程序故障（二级）；PATCH 温度上限 100 ℃、超温 105 ℃，让正在 120 ℃ 的 5 号超温切断（一级）；手动中止 2 号（三级）；确认一级报警；4 号再跑一次到完成 | alarm-l1、alarm-l2、alarm-page、alarm-l3、prog-aborted |
| E 反应 | 等 1、3 号进反应步，模拟器开始吸气，稳压补气，吸气量曲线出来 | main-f1/f2、prog-run、prog-done、plan-all、curve-*、rec-*、alarm-page、chan-full-run |

触屏连后台时，「页面名 → 状态」由新写的 `setup_page_net()` 按后台当前状态挑通道（见 §2 K4）。后台没有对应状态时退回最近的页面，并在 stderr 说明原因。

## 5. 还没解决的问题

1. **升温剩余时间估算**：程序的「剩 x min」按 C# 公式 3.5 ℃/min 估，开防超调逼近时实际要慢得多。4 号 25→35 ℃ 估「剩 1 min」，实际 9 min（C# 同样如此，没改）。建议后台按逼近参数（Δ、末段 0.2 ℃/min）估。
2. **方案总览 / 运行页的计划压力线**：气密、置换步骤的压力没有画进计划线，后台 `plan_of` 只按充压 / 放空拐点画。
3. **容积标定**：事件说明里各点压力仍是 psi（`ctl_volume_calib.cpp` 的 `pts`）。只出现在事件详情里，没改。
4. **审计事件直接显示 API 路径**：报警页「事件」里能看到「触屏命令 program.abort · 200 confirmed / DELETE /api/v1/…」。这是同 C# 的审计设计，操作员看着有点技术味。建议事件页默认过滤 `api.*` 类，或者换成人话。
5. **截图时的连接事件**：每次截图都会产生「接口客户端已连接 / 断开」两条事件，正常使用时只在开机时出现。
6. **泄漏测试不通过（leak-result）的界面**：模拟器每釜泄漏一样（0.4 psi/h），造不出不通过，连后台截的 leak-result 和 leak-pass 是同一状态。不通过那一页只在 `--sim` 预览里看过。
7. **吸气量曲线**：模拟器的吸气是一级反应的近似（40–68 psi 容量、时间常数 10 min），只用来验证界面链路，数值不代表真实化学。
8. **后台测试偶发失败**：联调早期 `api_server.sessions_and_estop_alias`、`file_download_with_range_and_telemetry_stream` 各出现过一次 404，后来连跑 4 遍全绿，原因未查（疑似测试里按「今天」取文件，跨分钟 / 时区时有竞态）。建议 api 模块负责人看一下。
9. **泄漏测试会让别的通道的程序故障**：泄漏测试进行中，其他通道程序的气路步骤（本次是 4 号的放空）立即按「泄漏测试进行中」故障中止，产生二级报警。这和 C# 的规则一致（`ctl_program_engine_gas.cpp` 注释写着「泄漏测试优先级不变」），没改。建议泄漏测试设置页在「有程序在跑」时提示一句，或者改成让程序排队等。
10. **远程控制期间触屏的控制命令被拒**：PC 拿到控制权后，触屏的程序下发等返回 409「远程控制中（实验室-PC2）」，这是设计行为。PC 不发心跳时，宽限 60 s 后自动回到本地（已验证）。触屏上被拒时只弹 toast，建议同时提示「点顶栏收回」。
11. **温度上限下调后**：已经在跑的 SP（120 ℃）高于新的上限（100 ℃）时，后台照常接受 PATCH，界面也照常显示 120。是否要提示由产品定。

## 6. 只能在板子上验证的

- 真 Modbus 时序（4 路 RS485、1.2 s 轮询、写阀死区 0.5 / 1.0 s）、模块离线 / 恢复，以及二级报警「模块离线」的真实弹出。模拟器里所有模块总在线，alarm-l2 用的是程序故障。
- 真实气路物理：减压阀出口压力、单向阀是否允许经 SV 反向放空（泄漏测试的「泄压未明显下降」提示），以及稳压补气的脉冲量和超调。
- 加热：AI-8 的真实输出 OP 与防超调逼近 / 放热判据（模拟器里 OP 是编的）、超温切断回读 At=4。
- reactor-hmi 在 X11 全屏下的触摸、字体（板子上的 Noto / Inter）、刷新性能（报警页、曲线页重建）、中英切换。
- Unix socket 的 uid 白名单（`--hmi-uid`）与触屏用户、`/media` 下真 U 盘的挂载识别、FAT32 写入。
- `nmcli` WiFi 扫描 / 连接、以太网 IP，在 macOS 上全是空的。
- GCC 9.4 编译（本次只在 Apple clang 上编了，代码没用 C++20）。
- SIGTERM / 服务重启时的安全停机，以及 PC 端真机（C# 控制软件）申请控制、心跳、宽限期满的完整流程。本次只用 curl 模拟了 request，没有心跳。
