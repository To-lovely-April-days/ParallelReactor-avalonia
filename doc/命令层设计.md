# 命令层设计（第 4 组：C1 / C2 / C5 / C11 / C25 + ControlArbiter）

> 分支 `fix-group4-arch`，基于 `fix-group2-3`。§0–§11 是设计稿；**批 B / C 已实现**，最终的入口 → 命令映射、白名单与实施偏差见 §12。
> 依据：`doc/对外通讯接口设计.md` §2.2、§5.1、§7、§11，附录 B，附录 C 的 C1、C2、C5、C11、C25；另参考第 4 组的触屏写入口清单。
> 本期**不做 HTTP 服务器**。目标是把远程接口要用的地基搭好：控制循环脱离 View、命令有返回值、校验放进命令层、PID 写入带显式档位、触屏写入口统一走一处，并加上控制权仲裁。

## 0. 结论摘要

1. **新增 `Commands/` 目录**，内容如下：
   - `OpResult` / `OpCodes`：结果与错误码；
   - `CommandSource`：命令来源；
   - `ControlArbiter`：控制权仲裁，纯逻辑；
   - `OperatorCommands`：按领域拆成 7 个 partial 文件；
   - `EntryAttributes`：入口登记。
2. **新增 `Service/ControlLoop.cs`**：在 `App` 启动时创建，持有 Tick、ClockTick 和开机预热三个 `DispatcherTimer`。
   - 另有纯逻辑的 `Service/TickGate.cs`，负责防重入和超时统计。
3. **所有触屏写入口都调用 `Ops.Try*(CommandSource.Local, …)`**，包括 RelayCommand、键盘确认回调、`SetRow` 的 Apply / ToggleApply / OnSelChanged、程序编辑、气路图点击。
   - 触屏端只做一件事：把 `OpResult` 转成 Toast，文字和级别与今天逐条一致。
4. **每个 `Try*` 都采用「同步头 + 异步尾」写法**：
   - 方法本身不是 `async`；
   - 第一条语句是仲裁；
   - 守卫、校验和第一次状态修改都在同一次 UI 线程调用里完成；
   - 需要等硬件的部分放在私有的 `*TailAsync` 里。
5. **默认 `ControlMode.Local`，本期没有切换界面**，只提供 `internal` 方法。所以本地操作员看到的行为不变。
6. **远程接口需要的额外守卫集中写成「严格守卫」**：`Strict(src)` 为真时才生效，本期只对 Remote 来源生效。将来要对本地也收紧时，只改一个开关。
7. **架构测试用源码扫描实现**，原因是测试工程不引用 Avalonia 主工程：
   - 每个 `[RelayCommand]` 必须标 `[WriteEntry]` 或 `[ViewEntry]`；
   - `WriteEntry` 的方法体必须调用它登记的 `Ops.TryX`；
   - `Try*` 不得是 `async`，并且必须先做仲裁；
   - ViewModels 里直接写设备的调用只允许出现在白名单方法里（只减不增）。
8. **分两批迁移**，两批改动的文件基本不重叠：
   - **批 B**：地基 + 主界面 / 抽屉 / 急停 / 气路 / 搅拌；
   - **批 C**：温控 PID / 设置 / 程序 / 泄漏 / 配方 / 报警。

## 2. 核心类型

### 2.1 OpResult（C2）

```csharp
public enum OpStatus { Confirmed, Accepted }   // §7.1：200 confirmed / 202 accepted

public sealed record OpResult
{
    public bool Ok { get; init; }
    public string Code { get; init; } = OpCodes.Ok;      // 失败时为 §11 错误码
    public string Message { get; init; } = "";          // 中文，直接用作 Toast / HTTP error.message
    public string Kind { get; init; } = "ok";           // Toast 级别 ok | warn | err（与现有 Toast(kind,…) 一一对应）
    public OpStatus Status { get; init; } = OpStatus.Confirmed;
    public object? Data { get; init; }                  // 成功：result；失败：error.detail
    public IReadOnlyList<string> Warnings { get; init; } = Array.Empty<string>();
    public bool Quiet { get; init; }                    // 触屏不弹 Toast（今天本来就没有 Toast 的路径，例如 PID 写入）

    public static OpResult Done(string msg = "", string kind = "ok", object? data = null);
    public static OpResult Accepted(string msg, string kind = "ok", object? data = null);   // 已下发、硬件结果稍后由事件通知
    public static OpResult Fail(string code, string msg, string kind = "err", object? detail = null);
    public static readonly OpResult Silent;             // Ok + Quiet
    public Task<OpResult> AsTask() => Task.FromResult(this);
}
```

**错误码 `OpCodes` 与 §11 同名。** 任务描述里用的名称按下表对应：

| 任务描述中的名称 | 实际使用（§11） |
|---|---|
| `OUT_OF_RANGE` | `PARAM_OUT_OF_RANGE` |
| `ESTOP_LATCHED` | `ESTOP_ACTIVE` |
| `INVALID_STATE` | `CHANNEL_STATE_INVALID`；通道无关时用 `CHANNEL_BUSY` |
| `NOT_FOUND` | `NOT_FOUND`；通道号不在 1..8 时用 `CHANNEL_NOT_FOUND` |

本期会用到的错误码：

- **仲裁**：`MODE_LOCAL`、`NOT_CONTROL_HOLDER`、`NOT_EXPOSED`
- **状态**：`ESTOP_ACTIVE`、`GAS_BUSY`、`GAS_OWNED_BY_OTHER`、`MANUAL_VALVE_ACTIVE`
- **通道**：`CHANNEL_NOT_FOUND`、`CHANNEL_NOT_INSTALLED`、`CHANNEL_ALARM`、`CHANNEL_PRESSURIZED`、`CHANNEL_PROGRAM_OWNED`、`CHANNEL_BUSY`、`CHANNEL_STATE_INVALID`、`CURVE_RUNNING`、`AUTOTUNE_ACTIVE`
- **过程**：`STIR_PROGRAM_OWNED`、`PROGRAM_RUNNING`、`LEAK_TEST_RUNNING`、`SYSTEM_BUSY`
- **参数**：`PARAM_OUT_OF_RANGE`、`PARAM_CROSS_CHECK`、`PREFLIGHT_FAILED`、`PROGRAM_INVALID`
- **硬件**：`HW_NOT_CONFIGURED`、`HW_OFFLINE`、`HARDWARE_WRITE_FAILED`；`HW_UNCONFIRMED` 只出现在 `Warnings` 中
- **其他**：`NOT_FOUND`、`INTERNAL`

另外有两个**只在本机使用**、不会出现在 HTTP 响应里的错误码，要补进 §11 的备注：

- `MODE_REMOTE`：远程控制中，触屏的启动 / 改设定被拒绝。
- `VALVE_BUSY`：上一个手动阀操作还没完成。

public readonly record struct CommandSource(SourceKind Kind, string ClientId = "", string ClientName = "")

### 2.3 ControlArbiter（§5.1）

```csharp
public enum ControlMode { Local, Remote }
public enum ActionClass { Control, Stop, Record, Reset }   // Control = 启动 / 改设定 / 下发；Reset = 急停复位
public enum Exposure { Remote, LocalOnly }                  // LocalOnly = 附录 B 中不对外的动作
public readonly record struct ArbiterDecision(bool Allowed, string? Code, string? Message);

public sealed class ControlArbiter
{
    // 模式与持有者成对放在锁里：任意线程可读可改（急停快速路径不在 UI 线程）
    public ControlMode Mode { get; }            // 默认 Local
    public string HolderClientId { get; }
    public string HolderName { get; }
    public string LastReturnReason { get; }
    public event Action? Changed;               // 在调用方线程、锁外触发；订阅方自己切回 UI 线程

    internal void EnterRemote(string clientId, string name);   // 本期只供测试 / 将来的 /control 授权调用
    internal bool ReturnToLocal(string reason);                // 返回之前是否为 Remote；急停快速路径调用

    public ArbiterDecision Check(ActionClass cls, CommandSource src, Exposure exp = Exposure.Remote);
        // 锁内取一次 (Mode, HolderClientId, HolderName) 快照，再调 Decide

    public static ArbiterDecision Decide(ControlMode mode, string holderId, string holderName,
                                         ActionClass cls, CommandSource src, Exposure exp);   // 纯函数
}
```

**`Decide` 判定表**（这张表就是测试表）：

| # | 条件 | 结果 | Code / Message |
|---|---|---|---|
| 1 | 来源 Remote，且 `exp == LocalOnly` 或 `cls == Reset` | 拒绝 | `NOT_EXPOSED`「该操作只允许在设备触屏上进行」 |
| 2 | `cls` 为 Stop / Record / Reset（经过第 1 行后只剩本地 Reset） | 允许 | — |
| 3 | Control，模式 Local，来源 Local | 允许 | — |
| 4 | Control，模式 Local，来源 Remote | 拒绝 | `MODE_LOCAL`「本地控制中 · 远程只能执行停止类和记录类操作」 |
| 5 | Control，模式 Remote，来源 Remote，且 `ClientId == HolderClientId` | 允许 | — |
| 6 | Control，模式 Remote，来源 Remote，不是持有者 | 拒绝 | `NOT_CONTROL_HOLDER`「当前控制权属于「{HolderName}」」 |
| 7 | Control，模式 Remote，来源 Local | 拒绝 | `MODE_REMOTE`「远程控制中（{HolderName}）」，Toast 级别 `warn`（§5.1 原文） |

补充说明：

- **租约**（`X-Control-Lease`、过期、grace）属于 HTTP 层，放到下一期，在第 5、6 行之前插入判断。
- **角色**（operator / estop）属于认证层，不放在仲裁里。
- **方向由调用方决定**：带开 / 关两个方向的命令（搅拌、手动阀控、各个阀、自整定、「超压时停止加热」）拆成 `bool on` 参数，在 `Try*` 内按方向选择 `ActionClass`。触屏的 Toggle 只负责计算目标方向，例如 `TrySetStir(Local, !StirOn)`。
- **急停收回控制权**（§5.3 第 4 条、§7.3）：`RequestEstop` 快速路径在置服务锁之后立即调用 `Arbiter.ReturnToLocal("急停")`，任何来源的急停都回到本地控制；复位后原持有者须重新申请，不能直接再启动加热 / 加压。收回时在「急停快速路径」事件里注明。
- **第 1 行先于第 2 行**：远程来源的停止类动作如果标了 `LocalOnly`（关手动阀、`TryExitApp`），也按第 1 行返回 `NOT_EXPOSED`。这与附录 B 一致，但比 §5.1「停止类两边都允许」更严：§5.1 的这句话只针对对外开放的动作。

### 2.4 CommandPolicy：严格守卫

```csharp
public static class CommandPolicy
{
    public static bool StrictLocal { get; set; } = false;   // 本期固定 false；测试可改
    public static bool Strict(CommandSource s) => s.IsRemote || StrictLocal;
}
```

**严格守卫**指 §7 标为「补」的检查，例如：

- 通道必须是 Ready / Done 才能启动加热；
- 报警通道不能启用；
- 曲线运行中不能改段；
- SP 必须小于 OverTemp；
- 跨通道写时跳过 `IsWorking` 的目标，或直接拒绝。

这些检查一旦对本地生效，就会改变本地操作员的体验。所以**本期只对远程生效**，在代码里统一写成 `if (CommandPolicy.Strict(src) && …)`。以后要决定本地是否也收紧，只改 `StrictLocal` 一个开关。

### 2.5 OperatorCommands 骨架

```csharp
public sealed partial class OperatorCommands
{
    private readonly MainViewModel _m;
    public ControlArbiter Arbiter { get; }
    public OperatorCommands(MainViewModel main, ControlArbiter arbiter);

    /// 每个 Try* 的第一条语句。非急停命令断言在 UI 线程（Dispatcher.UIThread.VerifyAccess）。
    private OpResult? Admit(CommandSource src, ActionClass cls, Exposure exp = Exposure.Remote)
    {
        Dispatcher.UIThread.VerifyAccess();
        var d = Arbiter.Check(cls, src, exp);
        return d.Allowed ? null : OpResult.Fail(d.Code!, d.Message!, d.Code == OpCodes.ModeRemote ? "warn" : "err");
    }
    private OpResult? ChannelOr(int id, out Reactor c);       // CHANNEL_NOT_FOUND
    private OpResult? ProgramOwned(Reactor c);               // 「RV{id} 正在执行程序 · 请先中止程序」warn，代码 CHANNEL_PROGRAM_OWNED
}
```

`MainViewModel` 新增两个属性：

- `public OperatorCommands Ops { get; }`：在构造函数末尾、各子 VM 构造完成后创建；
- `public ControlArbiter Arbiter { get; } = new();`

`OperatorCommands` 需要访问的 VM 成员要从 `private` 改为 `internal`，例如：

- `ApplyStir`、`BuildPreRun`、`RunChannelOf`、`StartBandHeatAsync`、`_stir`、`_valves`、`_press`
- `ManualValveAsync`、`GasLockedForManual`、`LogFileEvent`、`RealIo`、`IsAdmin`

这些只改可见性，不改逻辑。

### 2.6 「同步头 + 异步尾」写法（守卫与动作在同一次 UI 线程调用中完成）

```csharp
public Task<OpResult> TryStopHeat(CommandSource src, int id)
{
    if (Admit(src, ActionClass.Stop) is { } deny) return deny.AsTask();   // ① 仲裁：必须是第一条语句
    if (ChannelOr(id, out var c) is { } nf) return nf.AsTask();           // ② 守卫与校验：全部同步
    if (_m.Program.IsProgramOwned(id)) { … return OpResult.Done(…, "warn").AsTask(); }
    c.Profile.Stop(); c.Approach.Stop();                                  // ③ 第一次状态修改：仍是同一次调用
    if (c.State == ReactorState.Heating) c.State = ReactorState.Ready;
    _m.RefreshSchematic(); _m.Drawer.RaiseAll();
    return StopHeatTailAsync(id);                                         // ④ 之后才 await 硬件
}
```

**规则**（由架构测试检查，见 §6）：

- `public Task<OpResult> Try*(` 不得带 `async`；
- 方法体第一条语句必须是 `if (Admit(src, ActionClass.` 开头的仲裁；
- 异步尾的命名统一为 `*TailAsync`，是 `private async Task<OpResult>`。

### 2.7 触屏端：把 OpResult 转成 Toast

`MainViewModel` 增加两个方法：

```csharp
internal static CommandSource Src => CommandSource.Local;

/// 触屏入口统一调用：同步完成的结果当场 Toast（时序与今天相同，例如在 RaiseAll 之后），异步的等完成后 Toast。
internal void Local(Task<OpResult> t)
{
    if (t.IsCompleted) Show(t.IsCompletedSuccessfully ? t.Result : Internal(t.Exception));
    else _ = ShowWhenDoneAsync(t);
}
internal bool LocalOk(Task<OpResult> t);   // 同步部分被拒时返回 false，供需要回滚控件的入口使用（SetRow、StepField）
private void Show(OpResult r) { if (!r.Quiet && r.Message.Length > 0) Toast(r.Kind, r.Message); }
```

- 尾部抛出的异常转成 `INTERNAL`，记 `Alarm.Log("err", "系统", "命令异常", …)` 并弹 Toast，避免出现未观察的异常。
- **同步头抛出的异常**（例如不在 UI 线程时 `Admit` 的 `VerifyAccess`）在触屏路径上照旧冒泡（与改造前相同）。**远程适配层的约定**：先切到 UI 线程，再用 `OpResult.Guard(() => ops.TryX(src, …))` 调用——同步头与尾部的异常都转成 `INTERNAL`，返回的 Task 不会出错；`TryEstop` 例外，任意线程可直接调用。
- **`Try*` 内部禁止调用 `Toast`**，通过返回值表达结果。
- **异步通知仍然可以 Toast**，因为它们不是命令的返回，而是事件。以后会改走 EventStore（§2.2 第 5 点）。包括：
  - Tick 里的报警；
  - `ReportHeatStartFailed`；
  - 程序引擎、泄漏测试流程中的进度和结果。
- **`StopHeatAsync(id, okMsg)` 拆成两层**：
  - `internal Task<OpResult> StopHeatCoreAsync(int id, string okMsg)`：不弹 Toast，供命令使用；
  - 原来的 `StopHeatAsync` 保留为「Core + Show」，供程序引擎（`AbortProgram`）和 Tick 使用。
  - 这样 Toast 不会重复，也不会丢。
- **`CloseReactorValveAsync` 同样处理**：命令里用 `CloseReactorValveCoreAsync` 并返回 `OpResult`。

**Toast 缓冲（C1 的配套）**：控制循环会早于 View 订阅 `ToastRequested` 开始运行。改为：没有订阅者时把 Toast 暂存到队列（最多 20 条），第一个订阅者挂上时依次补发。用自定义 `event add` 访问器实现。

- `MainView` 在 `OnUnloaded` 退订、重新 `Loaded` 时再订阅，卸载期间的提示由 VM 暂存；
- 开机遮罩（`Splash`）盖住 `ToastHost`，而 Toast 只活 2.6 s，所以遮罩还在时到达的提示（含 VM 补发的开机提示「上次急停未复位」、预热期间的 Tick 提示）由 `MainView` 自己留着（最多 20 条），`HideSplash` 时再逐条显示。

## 3. ControlLoop（C1）

```csharp
public sealed class ControlLoop : IDisposable
{
    public ControlLoop(MainViewModel vm);           // 只依赖 Tick()/ClockTick()/SwitchTab/Setting.Pages
    public void Start();                             // 创建并启动 tick(1200 ms) 和 clock(1 s)
    public void Stop();                              // 停两个定时器和预热定时器；可重复调用
    public void StartWarmup(IWarmupHost host);       // View 的 Loaded 中调用；只运行一次
    public TickGate Gate { get; }                    // 防重入与超时统计（供诊断 / 将来的 /device/comm 使用）
}
public interface IWarmupHost { bool IsClosing { get; } void HideSplash(); }
```

### 生命周期

1. **`App.OnFrameworkInitializationCompleted`**：
   - 先 `var vm = new MainViewModel();`
   - 再 `_loop = new ControlLoop(vm); _loop.Start();`
   - 然后创建 MainWindow 或 MainView。
   - 控制循环与 View 是否加载无关。DRM 模式下 View 卸载后循环仍然运行，这正是 C1 的要求。
2. **退出时停止循环**：
   - 桌面模式只在 `desktop.Exit` 中调用 `_loop.Stop()`。**不挂 `ShutdownRequested`**：它之后关闭仍可能被取消（`Window.Closing` 或其他处理器置 `Cancel`），那时停掉循环会让程序继续运行却没有超温 / 超压联锁、急停补发与运行记录；
   - 单视图模式在 `AppDomain.ProcessExit` 中调用；
   - `ConfirmExit` 在 `desktop.Shutdown(0)` 或 `Environment.Exit(0)` 之前调用 `vm.Loop?.Stop()`。为此 `MainViewModel` 暴露 `internal ControlLoop? Loop`，由 App 赋值。
   - 停止之前，Tick 照常运行。今天 `ConfirmExit` 等待期间 Tick 也在跑，这一点保持不变。
3. **`MainView.axaml.cs` 的改动**：
   - 删除 `_tickTimer`、`_clockTimer`、`_warmTimer`、`WarmStep`、`FinishWarm` 中的定时器部分；
   - `OnLoaded` 改为 `App.Loop.StartWarmup(this)`，`MainView` 实现 `IWarmupHost`；
   - `OnUnloaded` 只设置 `_closing = true`，不再停止定时器。
4. **预热**：
   - 定时器由 `ControlLoop` 持有，节拍 250 ms，步骤顺序与 `WarmTabs` 和设置子页的逐页切换完全相同；
   - 结束时 `SwitchTab("home")`，设置页回到首个子页，再调用 `host.HideSplash()`；
   - 预热序列抽成 `ControlLoop` 内部的私有迭代器；
   - 没有 View 时（例如将来无头运行）不预热。
5. **ClockTick**：`MainViewModel` 构造函数末尾那一次同步调用保留，之后由循环每 1 s 调用一次。

### TickGate：防重入

```csharp
public sealed class TickGate
{
    public bool TryEnter();          // 已在 Tick 内时返回 false，并累加 Skipped
    public void Exit(TimeSpan took); // 记录本次耗时；超过 Interval 时累加 Overruns，并记录 LastOverrun
    public long Skipped { get; } public long Overruns { get; } public TimeSpan MaxTook { get; }
}
```

- 循环里这样调用：`if (!Gate.TryEnter()) return; var sw = …; try { vm.Tick(); } finally { Gate.Exit(sw.Elapsed); }`
- 今天 `Tick` 是同步方法，`DispatcherTimer` 本身不会重入。但以后有两种情况可能重入：
  - 嵌套消息循环；
  - 远程的「立即刷新」或测试直接调用 `Tick()`。
  门闸保证 Tick 不会重入。
- 异步轮询本来就有自己的防堆积机制（`TempService._polling`、`PollAsync(skipIfBusy)`），不变。
- 超时时每分钟最多记一条 `LogFileEvent("warn", "系统", "控制循环超时", …)`。
- **异常处理不变**：Tick 抛出的异常仍然冒泡到 Dispatcher。是否改为「捕获 + 计数 + 连续 N 次后急停」列为待决问题，见 §9。
- `finally` 里的超时记录自己 try/catch：写日志的异常不能顶替 Tick 的原始异常（否则真正的堆栈丢失）。

## 4. 显式档位的 PID 写入（C11）

`TempService` 新增：

```csharp
/// 写某通道某档的 PID。始终存入该档；只有当该档正是仪表当前生效的档（_lastBand[ch-1] == band）时才写仪表；
/// band == 界面显示档时同步界面的 P/I/D。返回是否写入了仪表。
public async Task<bool> SetPidAsync(int ch, int band, double p, double i, double d)
{
    var m = Channels[ch - 1];
    bool live = _lastBand[ch - 1] == band;
    var old = m.GetBand(band);
    m.SetBand(band, p, i, d);                       // ① 先存档（PidGen + 1）：等待期间 Tick 套档读到的已是新值
    if (band == _curBand) { m.P = p; m.I = i; m.D = d; }
    if (live)
    {
        int gen = m.PidGen;
        _lastBand[ch - 1] = -1;
        try { await c.SetPidAsync(loop, p, i, d); }
        catch { /* 没有更晚的修改时存档 / 界面回滚到 old */ throw; }   // 调用方记录「未生效」
        if (m.PidGen == gen) _lastBand[ch - 1] = band;   // 等待期间又被改过：保持 -1，下一 Tick 用最新值重写
    }
    PidsChanged?.Invoke();
    return live;
}
```

- **切档写入与手改的竞争**（评审补充）：`ApplyPidForBandAsync` / `StartChannelAsync` 在写仪表前记下 `TempChannel.PidGen`，写完后只有计数没变才把 `_lastBand` 记成该档，否则保持 -1，下一 Tick 用新值重写。这样「切档写入途中手改了目标档的 PID」不会留下「仪表是旧值、`_lastBand` 却说已生效」。
- **没有「界面显示档」便捷重载**：C11 要求便捷版只存在于 ViewModel；服务层只保留显式档位版本，触屏传 `Temp.CurrentBand`。

- **命令层**：`TrySetPid(src, ch, band, p, i, d)` 调用显式档位版本。触屏传入 `Temp.CurrentBand`。
- **行为变化（有意为之，需确认）**：今天的版本**总是**把界面档的 PID 写进仪表，并把 `_lastBand` 标记为界面档。如果仪表当前运行的是另一档，这次写入就把错误档的 PID 写进了正在加热的回路。这正是 C11 要修的问题。
- **新版本**：只存档。等下一次 `ApplyPidForBandAsync` 切到该档时才写仪表。
- **操作员能看到的部分不变**：设置事件「旧 → 新」照常记录，失败时照常记「未生效」，没有 Toast，持久化（`PidsChanged → PersistSoon`）也照旧。
- **冷启动的情况**：`_lastBand == -1` 时只存档，不写仪表。下一次启动加热会按目标温度套档写入，效果相同。
- `OpResult.Data` 里返回 `{ live: true/false }`。远程据此提示「已保存，切到该档时生效」。

### 6.2 运行期约束：源码扫描（ArchitectureTests.cs）

**为什么用源码扫描**：测试工程不引用主工程，以免引入 Avalonia，所以无法用反射加载 ViewModel 类型。

**入口登记用的特性**（`Commands/EntryAttributes.cs`）：

```csharp
[AttributeUsage(AttributeTargets.Method)] public sealed class WriteEntryAttribute(params string[] commands) : Attribute;
[AttributeUsage(AttributeTargets.Method)] public sealed class ViewEntryAttribute(string reason) : Attribute;
```

写法示例：

```csharp
[RelayCommand]
[WriteEntry(nameof(OperatorCommands.TryStartHeat))]
private void StartHeat() { if (Reactor is { } c) _main.Local(_main.Ops.TryStartHeat(Src, c.Id)); }
```

`nameof` 让改名时编译器报错。测试端读取的是源码里的字面量 `nameof(OperatorCommands.TryX)`。

**扫描规则**（扫描 `ViewModels/**/*.cs`、`Views/*.cs`、`Controls/*.cs`、`Commands/*.cs` 与四个服务类；方法体用一个简单的括号匹配器截取，同时支持表达式体 `=>`）：

| 规则 | 检查内容 |
|---|---|
| R1 | 每个 `[RelayCommand]` 方法必须**恰好**带 `[WriteEntry]` 或 `[ViewEntry]` 之一。漏标会失败，并打印 `文件:行 方法名`，对新增 RelayCommand 同样生效。 |
| R2 | `[WriteEntry(nameof(OperatorCommands.TryX), …)]` 的方法体里必须出现每个登记名的 `.TryX(` 调用。 |
| R3 | R2 中引用的每个 `TryX`，必须在 `Commands/OperatorCommands*.cs` 中有 `public Task<OpResult> TryX(` 声明。 |
| R4 | `Commands/OperatorCommands*.cs` 中：不得出现 `public async Task<OpResult> Try`；每个 `public Task<OpResult> Try*` 方法体的第一条非注释语句必须以 `if (Admit(src, ActionClass.` 开头。`TryEstop` 例外，它以 `if (Arbiter.Check(` 开头，并在白名单里单独列出。 |
| R5 | `Views/*.cs` 与 `Controls/*.cs` 中对 ViewModel 的调用。接收者是任何绑定到 `XxxViewModel` 的标识符（字段 `_vm`、属性、参数、`DataContext is XxxViewModel vm` 这类模式变量、`DataContext as …`，以及类型名本身的静态调用），调用链按 VM 源码里的属性类型逐段解析成「类型.方法」（`XxxCommand.Execute(` 解析为 `Xxx`）。被调方法必须带 `[WriteEntry]` 或 `[ViewEntry]`（登记集合按「类型.方法」，同名的别的方法不能蹭登记），或者在 `ViewReadAllowlist` 里（只读成员，带理由）。落在 VM 集合 / 子对象上的调用（例如 `vm.Steps.Insert(`）一律失败，除非是白名单里的只读调用。 |
| R6（只减不增） | 在 `ViewModels/*.cs` 中，下列 token 只能出现在 `ArchitectureTests.DeviceWriteAllowlist` 列出的「文件 + 方法」里。名单只允许减少；新增出现会失败，并提示「请经 OperatorCommands」。入口（`[RelayCommand]` / `[WriteEntry]` / `[ViewEntry]`）不得进白名单。 |
| R8 | `[ViewEntry]` / `[WriteEntry]` 方法体内不得直接改过程状态：`.State / .TSp / .PSp / .Vol / .SpMode / .RpmSp =`、`Profile.Start/Stop…(`、`Profile.X =`、`Steps.Add/Insert/Remove/RemoveAt/Move/Clear(`、`Steps[…] =`。`Ops.TryX(` 的实参（例如 `TryEditProgram` 的修改闭包，在命令层守卫之后执行）不算入口体。 |

R6 检查的 token 有三类：

- **手写项**：`StirOn =`、`StirRpm =`、`Settings.<Prop> =`，以及不写设备但改变过程 / 进程状态的原语 `BeginGas(`、`AbortGas(` / `AbortAllGas(`、`ShutdownApp(`；
- **服务写 API（自动生成）**：`TempService`（接收者 `Temp`）、`ValveService`（`_valves`）、`StirController`（`_stir`）、`PressureService`（`_press`）源码里的全部公开方法与公开 setter（含 `[ObservableProperty]` 生成的属性），排除 `Read*` / `Poll*` / `Get*` 与 `ServiceReadOnly`（`BandIndexForTemp`、`LiveBand`、`ExportBandPids`、`SelectBand`，各带理由）。服务新增写方法自动纳入检查，不必改测试；
- **白名单原语（传递闭包）**：白名单里每个方法名本身也是 token（构造函数与 `OnXxxChanged` 除外）。VM 里任何不在白名单的成员调用 `StartFixedHeat(`、`StopHeatAsync(`、`CloseAllValvesAsync(`、`AbortProgram(` 等同样违规——这些原语只能被命令层（不扫描）或白名单内的引擎 / 联锁方法调用。

白名单中的方法即 §5.11 所列，以及命令层调用的 VM 原语，见 §12.3。

## 9. 风险

1. **控制循环提前启动**：Tick 早于 View 订阅事件开始运行，早期 Toast 会丢失。对策是 §2.7 的 Toast 缓冲。`SchematicInvalidated` 没有订阅者也无害，因为 View 订阅时会全量刷新。
2. **DRM 下 View 卸载后循环继续运行**：这是有意的，安全监视不能依赖 View。需要确认 `RefreshSchematic` 和 `Drawer.RaiseAll` 在无 View 时没有副作用：它们只触发事件和属性通知，没有副作用。
3. **异步尾的时序**：今天 `StopHeat` 先改状态、再在硬件返回后 Toast。改造后同步头改状态、`Local` 等待尾部完成后 Toast，时序一致。**风险点在于漏掉 `Core` 拆分，导致 Toast 重复**。逐个对照 §5 的「返回」列，并在代码审查时检查「`Try*` 内没有 `Toast(`」（可加入 R4）。
4. **`SetRow` 回滚的重入**：`NumValue` setter 被拒后改回旧值，会再次触发 `TryApply`。要求回滚时直接写字段并调用 `OnPropertyChanged`，不经过 setter。ComboBox（`StepField.Value`）回滚时，Avalonia 可能在同一轮布局中覆盖回去，必要时用 `Dispatcher.Post` 延后一拍通知。
5. **键盘确认时重新判断守卫（K3）**：以前打开键盘后状态变化（例如程序开始执行），确认时会照样写入；现在会被拒绝。消息与打开键盘时的拒绝消息相同。这是**安全方向的变化**，列入 §10.2。
6. **`EstopLocked` 代替 `Estopped`**（Drawer 的 `Start` / `Enable`）：只在快速路径已经上锁、UI 流程尚未执行的毫秒级窗口内有区别。安全方向，列入 §10.2。
7. **C11 行为变化**：见 §4。如果现场习惯「改 PID 立刻写仪表看效果」，而界面档不等于运行档，现在不会立即生效。需要现场确认；可以在设置页给出「已保存，将在切到该档时生效」的提示。本期为了保持体验一致，`Quiet` 不提示，是否提示待定。
8. **源码扫描的脆弱性**：基于正则和括号匹配，对字符串里的括号或预处理指令敏感。约定：入口方法体保持简短（一两行转发），复杂逻辑放进命令层；测试失败信息要指向具体文件和行。
9. **`internal` 可见性扩散**：`OperatorCommands` 需要访问大量 VM 成员。如果后续发现耦合过重，可以把 VM 原语（`StartFixedHeat`、`StopHeatCoreAsync`…）进一步移到 `Service/ProcessPrimitives`。本期不做。
10. **Tick 异常策略**：今天 Tick 抛异常会冒泡到 Dispatcher，导致进程退出、systemd 重启。本期不改。待决：是否改为捕获、记录，并在连续 3 次后触发 `RequestEstop("控制循环异常")`。
11. **退出路径的缺口不在本期修复**：`ConfirmExit` 不调用 `AbortProgram`；SIGTERM 路径不停设备。这里只在 App 的退出钩子中停止循环。完整的 shutdown 处理需要另立条目。
12. **`ControlArbiter` 本期没有切换界面**：`MODE_REMOTE` 这条路径在界面上走不到，只能靠单元测试和 §8 的自检覆盖。下一期加顶栏模式显示时，要用真机再验证一遍。

## 10. 本地操作员的行为

### 10.1 必须保持不变

- 每个入口的 **Toast 文字和级别**与 §5 引用的现有字符串逐字一致，包括 warn / err 的区分（例如 `OwnedByProgram` 是 warn，`HeatBlockReason` 是 err，停止加热成功是 warn）。
- **Toast 时机**：同步拒绝或成功立即弹出；等待硬件的命令在硬件返回后弹出。
- **没有 Toast 的路径仍然没有**：PID 写入、`EditStirRpm` 在搅拌未运行时、草稿编辑被禁用时。
- **键盘**：打开时的范围提示、确认时的限幅、急停关闭键盘并丢弃回调（Estop.cs:295）都不变。
- **对话框流程**：预运行检查、程序确认、急停面板、复位确认、退出确认都不变。确认按钮的连点保护（`_pendingRun` 取走即清空）不变。
- **`StopAll` 不停搅拌**；`ConfirmRun` 在需要时自动开搅拌；`AbortProgram` 关闭全局搅拌（H5）。这些都不变。
- **`CopyConfigToAll` 和配方应用的筛选规则**（跳过 Idle 和被程序占用的通道）不变，本地仍然不限幅。
- **抽屉曲线段**在曲线运行中仍然可以编辑（K4 只在严格守卫下拒绝）。
- **报警通道仍然可以被启用**（K6 只在严格守卫下拒绝）。
- **设置数值行**：仍然是 1.5 s 防抖记日志，退出时才落盘；「超压时停止加热」立即落盘。
- **事件记录**：内容与条数不变，只有一项例外，见 §10.2 第 4 条。
- **Tick、Clock、预热**：节拍（1.2 s / 1 s / 250 ms）、预热页序和结束停在首页都不变。开机遮罩期间 Tick 已经在运行，这一点今天也是如此。
- **急停快速路径**：仍然可以从任意线程调用，不进入 UI 线程，不受仲裁影响。

### 10.2 有意的细微变化（都是安全方向或修正，需评审确认）

1. **键盘确认时重新判断守卫**（K3）：涉及 Tsp 的程序占用、程序页 `CanEdit`、自整定的 `HeatBlockReason`。
2. **Drawer 的 `Start` / `Enable` 改判 `EstopLocked`**，原来判 `Estopped`。
3. **C11**：手改 PID 只有在改的是仪表当前生效档时才立即写仪表，见 §4。
4. **程序页修改全局转速多记一条「设置 · 搅拌转速」事件**，与工具栏入口一致。

### 12.4 批 C 与设计稿的偏差

1. **`SetRow` 的结果去向**：三个写回调（`TryApply` / `ToggleApply` / `OnSelChanged`）返回 `Task<OpResult>`，另有 `Sink`（= `MainViewModel.Local`）。同步被拒时在 setter 里直接写字段回滚并通知（立即一次 + `Dispatcher.Post` 一次）；键盘确认用 `SetRow.Submit(v)`，结果交给键盘的 `ResultSink`。
2. **设备设置项的写入搬进命令层**：`ApplyStir*Async` / `ApplyStirRampMs` / `ApplyPressFullScaleMPa` 从 `MainViewModel` 删除，成为 `TrySetSetting` 的私有尾部；Toast 文字不变。驱动器没有回读值时今天不提示，现在返回 `HARDWARE_WRITE_FAILED` 且 `Quiet`（触屏仍不提示，远程能拿到失败）。
3. **`ProgramRunGuard.Check`** 返回 `(Code, Message)?`，`Reason` 改为 `Check()?.Message`；`ProgramRunInput` 增加 `GasBlockCode`，气路公共检查的错误码随之透传（缺省为 `GAS_BUSY`）。
4. **`TryEditProgram` 的锁定提示**：程序执行中为 `CHANNEL_PROGRAM_OWNED`「程序执行中 · 已锁定为只读」，通道运行中为 `CHANNEL_BUSY`「该通道正在运行 · 程序已锁定为只读」（与界面 `LockHint` 同文），均为 warn + `Quiet`。
5. **`StepField.Gate`** 只用于下拉框（`Value` setter）；`SetNumber` 是原始写入，键盘路径在回调里显式经过 `TryEditProgram`，避免嵌套过闸。
6. **`EditGlobalStir(apply)`**：程序页「搅拌」行与工具栏共用 `TrySetStirRpm`，多记一条「设置 · 搅拌转速」事件（§10.2 第 4 条）；成功结果在程序页置为 `Quiet`——今天程序页改转速没有 Toast，工具栏入口在搅拌运行中才提示，不能因为统一命令而多出一条 Toast。
7. **`TryStartLeakTest(ids, testPsi?)`** 调用 `LeakViewModel.RunAsync(ids, target)`：所选通道在面板格子里不可选时（例如远程发起、面板很久以前打开）按当前状态重建格子再勾选；本地路径格子不变。
8. **报警编号**：`AlarmItem.Id` 为本次运行内递增的字符串，`TryAckAlarm` 按它查找；`AlarmViewModel.Main` 由 `MainViewModel` 赋值，`Ack` 经命令层。
9. **配方**：`TryApplyRecipe` 接受配方名或 Id；`RecipeViewModel.Apply` 只在命令成功后关闭面板（顺序与今天一致：先关面板再提示）。
10. **`TryReplaceProgram`** 增加 `ProgramStep.FromSnapshot`；整体替换后若是当前通道，清掉选中步骤并刷新。
11. **Remote 模式自检**（§8）按设计稿的降级方案做成静态保证：R7 核对每个 `Try*` 首句仲裁的类别与 Exposure，配合 `ControlArbiterTests` 的 48 组判定表。运行期的反射自检没有做。
12. **测试工程**为链接 `Models/AppSettings.cs` 加了 `TestStubs.cs`（`ApproachParams` 替身，签名须与 `Models/HeatApproach.cs` 一致）。
13. **P3 控制权（`api-phase3`）**：新增 `TryGrantControl / TryDenyControl / TryTakeBackControl`（Record · 本地：只改 `Commands/ControlLease.cs` 的租约状态机，不碰设备；§5.1「只有本地可以允许 / 切回」），R7 登记表同步。远程写命令由 `Api/Hmi/HmiRemoteCommands.cs` 经 `Api/Hmi/UiCommandBridge.cs`（接口层进 UI 线程的唯一入口）调用对应 `Try*`，`CommandSource.Remote(令牌名, 客户端名)`；`Reactor.StartedBy` 在 `TryEnableChannel / TryStartHeat / TryStartProfile / TryRun` 写入、`TryStopChannel / TryStopAll / 急停` 清空（`onRemoteLost = stopHeat` 的依据）；`TryBeginSession(src, testId, note?)` / `TryAddMarker` 把来源与客户端写进会话 manifest；`TryStartLeakTest` 的 Data 带 `runId`。架构测试 `ApiArchitectureTests.Api_HmiAdapter_DispatcherOnlyInBridges` 把「HmiApiSources 只在 PreflightAsync 用 Dispatcher」放宽为「Api/Hmi 下只有 UiCommandBridge.cs / ControlBridge.cs 可用 Dispatcher」。

### 12.5 本地操作员可见的变化（批 C 部分，补充 §10.2）

1. 自整定：确认键盘时重新判断启动加热检查（K3，§10.2 第 1 条已列）。
2. 程序页：程序开始执行后，已打开的字段键盘确认被拒（不提示，与按钮被禁用一致）。
3. 其余入口的 Toast 文字、级别、时机与今天一致；事件记录只多 §10.2 第 4 条那一条。命令内先记事件、再由触屏提示，二者顺序与今天相反（例如「程序下发被拒绝」），屏幕上看不出差别。

**第 4 组评审修正后新增的可见变化：**

4. 全部停止：阀门全关失败的提示改为等加热与阀门两条总线都有结果后再弹（原先阀门失败当场弹）；两者都失败时合成一条「停止加热输出未确认 … · 阀门全关写入失败 …」。报警记录文字不变。
5. 设置页 +/−：当前值在范围外（设置文件未限幅、开机从驱动器回填）时，按一下回到范围边界并写入；原先算出的值仍越界，被拒绝并回滚，+/− 永远走不回来。
6. 开机提示：遮罩期间的 Toast（例如「上次急停未复位」）在遮罩收起后显示；原先在遮罩下 2.6 s 就消失了。
7. 曲线升温：启动链同步失败（快速路径急停已置锁）时曲线一并停下；原先会留下「曲线在跑、仪表不出力」。
8. PID：切档写入途中手改了目标档的 PID，下一 Tick 用新值重写仪表；原先仪表可能一直留着旧值。

只在 Remote 模式下才有区别（本期没有切换入口）：急停收回控制权；远程控制中本地可以打开「超压时停止加热」。
